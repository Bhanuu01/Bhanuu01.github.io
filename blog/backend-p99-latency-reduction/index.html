Backend engineering

What I learned from redesigning backend APIs to reduce P99 latency

May 19, 2026 · 5 min read

Average latency often hides the user experience that actually gets shipped. Tail latency is what shows up when a system is stressed, and in many backend systems the real problem is not one slow line of code but a design that forces the request path to own too much synchronous work.

Where the pain was coming from

At SalesUp, some API flows were handling work inline that did not need to happen before the response returned. That design made request paths heavier than they needed to be and caused slow operations to compete directly with interactive traffic.

What changed

The most important shift was architectural, not syntactic. The API moved closer to a coordinator model: validate the request, persist the right state, queue the background work, and return a stable contract quickly instead of trying to finish everything synchronously.

The point of async work is not that it sounds modern. The point is that some responsibilities should not live on the request path at all.

That redesign improved system throughput and reduced P99 latency because long-running operations stopped competing directly with the traffic that needed fast responses. It also created cleaner retry boundaries and made failure handling easier to reason about.

What stayed with me

The most useful lesson was that latency tuning is often a question of systems boundaries, not just local optimization. That perspective still shapes how I think about ML pipelines and infrastructure today.

Proof

Throughput increased by 40%.

P99 latency dropped by 25%.

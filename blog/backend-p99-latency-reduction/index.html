Backend engineering

What I learned from redesigning backend APIs to reduce P99 latency

May 19, 2026

The most useful thing I learned from backend performance work at SalesUp was that tail latency is usually an architecture problem before it is a code problem. We had API flows doing too much work inline, and the result was that slow operations were directly competing with traffic that needed quick responses.

Where the delay came from

Some of the request paths were trying to finish work that did not actually belong in the response cycle. That made the APIs heavier than they needed to be and pushed long-running operations into the same path as user-facing traffic.

What we changed

The main shift was to treat the API as a coordinator. Validate the request, persist the right state, queue the background work, and return a stable response instead of trying to finish everything synchronously. That reduced contention on the request path and made retries and failure handling cleaner too.

In practice, the work that moved off the request path included slower campaign-generation and follow-up automation tasks that did not need to block the user-facing response.

What stayed with me

I still think about this project whenever latency discussions get too local. Sometimes the fix is faster code. Just as often, the real question is whether the system boundary is in the wrong place.

Proof

Throughput increased by 40%.

P99 latency dropped by 25%.

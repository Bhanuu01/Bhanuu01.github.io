Fused Linear Attention

A hardware-aware attempt to reduce transformer inference overhead at the kernel level.

CUDA C++ · PyTorch · NSight · H100

This project came from a systems question rather than a benchmark alone: what happens when QKV projection and attention are forced into a tighter CUDA execution path so intermediate data moves less through HBM? That framing made the project useful to me even before the final numbers were in, because it required thinking about bottlenecks through measurement instead of intuition.

Problem

Standard inference paths split projection and attention into separate stages. Each stage writes intermediate tensors back to HBM and then reads them again. On modern accelerators, that traffic can become the real constraint long before arithmetic throughput is exhausted.

Approach

I designed a fused execution strategy that combines QKV projection and scaled dot-product attention into a single kernel path, then validated correctness against PyTorch references across multiple sequence lengths. The work also included T=64 tiling decisions, shared-memory padding to avoid bank conflicts, and NSight-based profiling to track where time and bandwidth were actually going.

Memory path sketch

Standard path QKV projection write intermediate tensors to HBM run attention as a separate stage
Fused path keep projection and attention closer together cut repeated HBM writes and reads profile what bottleneck remains after fusion

What the numbers said

The implementation reduced HBM bandwidth by 11–55% depending on sequence length. On the best short-sequence runs, the fused path reached 1.22x–1.41x speedup over the reference path and reduced peak GPU allocation by 85–91%. The gains were real, but not uniform. Once the bandwidth cost came down, the profiler still pointed to scalar fp32 projection loops as the next limiter.

Numbers

Metric Result Why it mattered
Correctness 11 / 11 tests passed, max absolute error ≤ 1.5 × 10-7 Confirmed that the fused kernel matched the PyTorch reference path closely enough to trust profiling.
HBM traffic 11–55% reduction, with the strongest measured cut around 54.6% Supported the original hypothesis that repeated global-memory movement was a real cost.
Short-sequence speed 1.22x–1.41x over the unfused reference path Showed that fusion could translate into real runtime wins in the right regime, not only lower bandwidth.
Peak allocation 85–91% lower peak GPU memory allocation Made the kernel behavior more practical to reason about beyond raw runtime alone.
Profiler signal Remaining scalar fp32 projection loops became the next visible bottleneck Kept the project honest about why bandwidth savings did not automatically solve the whole problem.
The value of the project was not only the bandwidth reduction. It was learning how to reason clearly about GPU bottlenecks once the profiler starts disagreeing with your first intuition.

Why it matters

This is the strongest example on my site of the kind of work I want to keep doing: low-level, empirical, and tied to real performance behavior rather than abstract interest in acceleration.
